# General-Admin 部署问题排查手册

本文档记录部署到 Linux 服务器（尤其是 `jdwan`：`117.72.147.216:22`）失败时的标准排查流程。后续推送、迁移、启动失败，优先按本流程定位，不要直接清库。

---

## 一、先看错误类型

| 报错关键词 | 大概率原因 | 排查章节 |
|---|---|---|
| `远程命令超时（300s）：bash ./migrate-db.sh` | 数据库迁移卡住 / 数据库连不上 | 第 3 节 |
| `SSH 连接失败` / `Connection timed out` | 网络、防火墙、端口、服务器未开机 | 第 2 节 |
| `rsync 失败` / `Fabric 上传失败` | 权限、空间、文件被占用 | 第 4 节 |
| 后端启动后无进程 | 环境变量、端口占用、数据库连不上 | 第 5 节 |

---

## 二、排查 SSH 是否可达

这是第一步。如果 SSH 都进不去，所有后续操作都走不通。

```bash
# 1. 基础连通性
ping -c 4 -W 3 117.72.147.216

# 2. 端口是否开放
nc -vz -w 5 117.72.147.216 22

# 3. 直接用 ssh 登录
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
  -o ConnectTimeout=10 \
  root@117.72.147.216 -p 22
```

### 判断标准

- `ping` 通 + `ssh` 能进 → 继续第 3 节
- `ping` 不通 → 服务器网络/防火墙/关机，联系运维或换网络环境
- `ping` 通但 `ssh` 报 `Connection timed out during banner exchange` → SSH 端口被封或 sshd 未启动
- `ssh` 报认证失败 → 检查 `Script/deploy-to-linux.py` 里的 `password` / `identity_file`

## 三、排查数据库迁移超时

当部署脚本卡在 `🔄 执行数据库迁移...` 并最终报 `远程命令超时（300s）`，通常是 `DbMigrator` 没能在 300 秒内完成或根本没有连上数据库。

### 3.1 确认目标数据库连接串

部署包里的连接串在这里：

```bash
# 本地构建产物
build/backend/dbmigrator/appsettings/02-connection-strings.jsonc

# 远端部署目录
/home/wong/Desktop/Code/CsharpLang/General-Project/backend/dbmigrator/appsettings/02-connection-strings.jsonc
```

常见配置示例：

```jsonc
{
  "Database": {
    "Provider": "PostgreSql"
  },
  "ConnectionStrings": {
    "Default": "HOST=124.222.232.50;Port=30007;Database=general_admin;Username=postgres;Password=xxx;SslMode=Disable"
  }
}
```

### 3.2 在服务器上测试数据库连通性

SSH 登录后执行：

```bash
# 用 nc 测试端口是否通
nc -vz -w 5 124.222.232.50 30007

# 如果有 psql，直接连（用实际连接串里的参数）
psql "host=124.222.232.50 port=30007 dbname=general_admin user=postgres password=xxx sslmode=disable" -c "SELECT 1;"
```

### 3.3 手动执行迁移脚本看输出

SSH 登录后执行：

```bash
cd /home/wong/Desktop/Code/CsharpLang/General-Project/backend
bash -x ./migrate-db.sh
```

如果一直无输出，说明程序在尝试连接数据库阶段就卡住了；如果有 EF Core 迁移日志，看具体卡在哪一条 SQL。

### 3.4 直接运行 DbMigrator 看日志

```bash
cd /home/wong/Desktop/Code/CsharpLang/General-Project/backend/dbmigrator
dotnet General.Admin.DbMigrator.dll --environment Production
```

> 注意：直接运行会读取 `appsettings/` 下的配置，确认 `02-connection-strings.jsonc` 是目标环境要用的配置。

### 3.5 迁移卡住的常见原因

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全无输出，CPU 很低 | 连不上数据库（网络/防火墙/PG 未启动/连接串错误） | 检查连通性和连接串 |
| 打印迁移名后卡住 | 某条迁移 SQL 慢 / 锁表 | 查数据库 `pg_stat_activity` |
| 报错 `37P01` / 关系已存在 | 历史迁移记录与数据库实际结构不一致 | 对比 `__EFMigrationsHistory` |
| 开发环境和服务器连同一个库 | 两边同时改结构或种子数据 | 拆分数据库，或临时用独立库测试 |

### 3.6 数据库锁排查（PostgreSQL）

```sql
SELECT pid, state, query_start, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE datname = 'general_admin'
ORDER BY duration DESC;
```

如果看到长时间 `active` 或 `idle in transaction` 的会话，考虑先终止（谨慎）：

```sql
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'general_admin' AND pid <> pg_backend_pid();
```

## 四、排查文件上传/同步失败

部署脚本优先用 rsync，密码服务器回退到 Fabric 差量上传。常见报错：

- `rsync 失败` → 检查本机和远端是否都有 rsync，密钥是否正确
- `文件较多（N 个），改用单包上传...` 后卡住 → 可能是 Fabric tar 解压慢或磁盘满
- 上传完成但进程未更新 → 旧进程占用 DLL，未正确停止

检查磁盘空间：

```bash
ssh root@117.72.147.216 'df -h /home/wong'
```

## 五、排查后端启动失败

迁移成功后，启动失败通常表现为：脚本提示 `⚠️ 未检测到后端进程`。

### 5.1 看日志

```bash
ssh root@117.72.147.216 \
  'tail -n 100 /home/wong/Desktop/Code/CsharpLang/General-Project/backend/logs/backend.log'
```

### 5.2 常见启动失败原因

| 现象 | 原因 | 处理 |
|---|---|---|
| `Address already in use` | 5007 端口被占用 | `pkill -f General.Admin.HttpApi.Host.dll` 后重试 |
| 数据库连接失败 | 连接串错误或数据库未启动 | 回到 3.2 |
| 证书/OpenIddict 报错 | 证书配置与部署环境不匹配 | 检查 `appsettings/01-openiddict.jsonc` |
| 权限 denied | 文件属主不对 | `chown -R wong:wong /home/wong/Desktop/Code/CsharpLang/General-Project` |

## 六、是否需要清库？

**清库是最后手段，会丢失 `general_admin` 数据库里的所有数据。**

在以下情况之前，不要直接清库：

1. 已确认 SSH 可达
2. 已确认数据库服务本身正常
3. 已尝试手动执行迁移并保留日志
4. 已确认不是端口占用、进程未停止、文件权限等更简单的问题
5. 已备份（如果数据重要）

如果需要清库，部署脚本已经支持 `--fresh-db`：

```bash
python3 Script/deploy-to-linux.py jdwan --fresh-db
```

它会读取 `build/backend/dbmigrator/appsettings/02-connection-strings.jsonc` 里的连接串，DROP + CREATE 数据库，然后重新跑迁移。

> 注意：`--fresh-db` 只清 PostgreSQL 数据库。SQLite 文件不会被这个流程自动清，需要手动删 `backend/data/general-admin.db`。
