# 五期建设总规划：AI 智能能力区

> 版本：v1.0  
> 状态：规划中  
> 定位：独立 AI 模块，不混入 Platform、Project、Business

## 1. 建设背景

当前系统已经完成平台治理、项目执行、经营管理和 PMP 基础能力建设。项目中已经沉淀了章程、WBS、任务、排期、工时、RAID、质量、变更、基线、EVM、会议、文档、经营链、预警等结构化数据。

五期 AI 建设的目标不是做一个通用聊天机器人，也不是做一个编程 Agent 平台，而是围绕企业项目管理场景提供可审计、可控、可私有化部署的智能辅助能力。

OpenCowork 可以作为产品灵感来源，重点吸收：

- Provider 独立配置
- 澄清模式
- 规划/架构管控模式
- MCP 客户端
- 技能系统
- 记忆系统
- 定时智能体
- 多渠道交付思路
- 工具调用审批

不直接保留：

- 编程 Agent 能力
- 本地文件系统随意读写
- Shell 执行能力
- Electron 本地运行时架构

General Admin 的 AI 能力应在服务端运行，并受 ABP 权限、租户、审计、数据范围和成本控制约束。

## 2. OpenCowork 架构参考与映射

OpenCowork 的架构可以概括为：主进程承接系统能力，渲染进程承接 Agent Loop 和 Tool Registry，Preload 作为安全桥接，Shared 定义跨进程协议。General Admin 是 ABP 服务端系统，不能照搬 Electron 架构，但可以吸收它的能力分层。

| OpenCowork 架构点 | 参考价值 | General Admin 落地方式 |
|---|---|---|
| Provider System | 多供应商、多模型、基础测试、模型选择 | `AiProvider`、`AiModel`、模型网关和默认模型策略；真实连通性随模型调用网关落地 |
| Agent Loop | 对话、流式输出、模式切换、上下文管理 | `AiConversation`、`AiMessage`、澄清模式、规划模式 |
| Tool Registry | 工具白名单、工具描述、工具调用审批 | `AiToolDefinition`、`AiToolInvocation`、`AiToolRegistryService` |
| MCP Manager | 连接 MCP Server，发现 tools/resources/prompts | `AiMcpServer`、`AiMcpTool`、`AiMcpInvocation`、`AiMcpService` |
| Cron Scheduler | 定时触发 Agent 任务并保存运行记录 | 只借鉴产品形态；调度统一复用 Platform Scheduler |
| Channel Manager | 飞书、钉钉、企业微信等消息平台插件 | 六期 `IntegrationConnectorRegistry` 和具体连接器 |
| Skills | 给 Agent 的可复用操作说明，不是新工具 | 七期 General Admin Skill 包 |
| Memory | 用户、项目、全局记忆 | `AiMemory`、项目记忆、组织记忆、用户记忆 |
| Plan / Goal | 计划确认、目标追踪、可勾选步骤 | 澄清模式、规划模式、AI 自动化任务草稿 |

关键结论：

- OpenCowork 的 `Skill` 是操作说明，不是工具协议；General Admin 七期只做 Skill 包，不在五期把 Skill 当作可调用工具。
- OpenCowork 的 `Cron` 是 Agent 定时运行时；General Admin 已有 Platform Scheduler，所以五期不新建第二套调度中心。
- OpenCowork 的 `Channel` 属于消息平台连接能力；General Admin 统一放到六期 Integration 模块。
- OpenCowork 的 `MCP` 可以进入五期 AI 模块，但必须受租户、权限、工具白名单和审计控制。

|---|---|---|

## 5. 设计原则

1. AI 是独立模块，不是 Platform 的附属配置。
2. AI 不直接拥有 Project/Business 数据，只通过受控上下文和工具访问。
3. AI 输出默认是草稿，不默认写回业务数据。
4. 涉及项目状态、风险、变更、经营金额的写操作必须人工确认。
5. 指标口径仍由后端业务服务定义，AI 只解释、归纳和建议。
6. AI 必须保留输入、上下文、工具调用、输出和成本记录。
7. 支持私有化部署，Provider 可替换，可禁用公网模型。
8. 提示词、记忆、知识源必须可审计、可关闭、可删除。
9. AI 自动化任务只保存 AI 任务定义和运行结果，不负责 Cron 调度。
10. 外部消息平台不在 AI 模块直接实现，统一交给六期 Integration。
11. Provider 网关、工具调用、限额检查和关键输出解析必须有可自动化回归验证，不依赖真实外部模型才能发现基础协议退化。

## 6. 核心能力范围

### 6.1 Provider 与模型管理

支持配置：

- OpenAI Responses 协议
- Anthropic Messages 协议

五期不再保留旧的 `OpenAICompatible`、`AzureOpenAI`、`LocalGateway`、`PrivateModel` 等 Provider 类型。DeepSeek Anthropic 兼容地址按 `AnthropicMessages` 协议配置，例如 `https://api.deepseek.com/anthropic`；本地或内网模型网关也必须选择并实现上述两类标准协议之一。

模型配置字段建议：

| 字段 | 说明 |
|---|---|
| ProviderCode | 供应商编码 |
| ModelCode | 模型编码 |
| DisplayName | 显示名称 |
| Endpoint | API 地址 |
| ApiKeySecret | 加密密钥引用 |
| Capability | chat、vision、embedding、toolCalling |
| ContextWindow | 上下文长度 |
| InputPrice | 输入价格 |
| OutputPrice | 输出价格 |
| IsDefault | 是否默认 |
| IsEnabled | 是否启用 |
| TenantScope | 租户范围 |
| RateLimit | 限流配置 |
| FallbackModelId | 降级模型 |

### 6.2 AI 会话

会话不是简单聊天窗口，应支持场景化模式。

| 模式 | 说明 | 第一版建议 |
|---|---|---|
| 澄清模式 | 先提问，补齐目标、约束、范围，再生成结果 | 必做 |
| 规划模式 | 分解目标、列出步骤、形成可勾选计划 | 必做 |
| 执行辅助模式 | 生成周报、会议纪要、风险分析、经营解释 | 必做 |
| 知识问答模式 | 基于项目详情、文档、会议、经营数据问答 | 必做 |
| 管控模式 | 类似 ACP/AOP，进行上下文收集、计划、工具调用、草稿输出、人工确认 | 第二阶段 |

### 6.3 AOP/ACP 流程借鉴

OpenCowork 中 `acp` 模式可借鉴为“架构管控/任务分解模式”。在本系统中建议定义为：

`AI Orchestration Pipeline`

流程：

1. 识别用户目标
2. 澄清缺失信息
3. 检查用户权限
4. 收集项目/经营/文档/会议上下文
5. 生成计划
6. 展示计划给用户确认
7. 调用只读工具或生成草稿
8. 对写回动作进行人工确认
9. 写入业务对象或形成待办
10. 记录审计、成本和效果反馈

### 6.4 工具与能力注册

AI 工具必须是白名单注册，不允许模型自由访问系统接口。

工具调用记录必须能追溯到会话和最终助手消息。用户在 AI 会话页看到工具调用摘要后，应能直接打开调用明细，核对工具输入、输出、引用来源、耗时和错误信息。

只读工具：

- 读取项目概览
- 读取项目 WBS 与任务
- 读取排期与里程碑
- 读取 RAID
- 读取质量检查
- 读取变更请求
- 读取 EVM 快照
- 读取工时统计
- 读取会议纪要
- 读取项目文档摘要
- 读取经营项目概览
- 读取合同、预算、回款、发票、验收摘要

受控写工具：

- 生成项目周报草稿
- 生成会议纪要草稿
- 生成风险登记草稿
- 生成问题处理建议
- 生成变更影响说明草稿
- 生成经营风险说明草稿
- 生成 PMO 治理行动建议

第一版不开放：

- 自动修改项目状态
- 自动审批变更
- 自动修改合同或预算
- 自动发送外部通知
- 自动执行脚本或命令

### 6.5 MCP 能力

AI 模块需要同时考虑两类 MCP 能力：

| 能力 | 说明 | 优先级 |
|---|---|---|
| MCP Client | 连接外部 MCP Server，把外部工具接入 AI 会话 | 高 |
| MCP Server | 把 General Admin 的项目/经营能力以受控工具形式暴露给外部 Agent | 中 |

MCP 配置必须支持：

- stdio
- SSE
- Streamable HTTP
- 启用/禁用工具
- 工具权限范围
- 超时配置
- 调用日志
- 租户级隔离

### 6.6 记忆与知识源

记忆必须分层：

| 层级 | 示例 | 规则 |
|---|---|---|
| 组织记忆 | 公司项目管理规范、报告模板、风险分类标准 | 管理员维护 |
| 项目记忆 | 项目目标、关键约束、重要决策、经验教训 | 项目内可见 |
| 用户记忆 | 用户偏好的报告格式、常用语气、关注指标 | 用户可查看和删除 |
| 场景记忆 | 会议纪要、风险复盘、变更原因 | 需要来源引用 |

知识源：

- 项目文档
- PRD 文档
- 会议纪要
- 质量检查记录
- 变更记录
- 经营报告
- 管理制度

第一版可以先做结构化摘要与引用，不强制一次性接入向量库。后续可扩展 PostgreSQL pgvector 或独立向量数据库。

### 6.7 AI 场景模板

五期这里的“技能”指 AI 模块内的场景模板和提示词编排，不等同于 OpenCowork/Codex 的 `SKILL.md`。真正面向外部 Agent 的通用 Skill 包放到七期。

建议首批场景模板：

- 项目周报生成
- 会议纪要整理
- 风险分析
- 问题根因分析
- 变更影响说明
- PMO 项目组合摘要
- 经营风险解释
- 回款催收建议
- 干系人沟通文案
- 项目复盘报告

场景模板配置应包含：

- 场景
- 输入要求
- 上下文来源
- 输出格式
- 是否允许工具调用
- 是否允许写回草稿
- 权限要求

### 6.8 AI 自动化任务

借鉴 OpenCowork Cron Agent 的产品形态，但不新增调度器。General Admin 已有 `PlatformScheduledJob`、触发器、执行记录和 `IPlatformScheduledJobHandler`，五期只新增 AI 自动化任务定义和 AI 运行结果。

边界：

- `AiJob` 保存 AI 自动化任务定义、上下文范围、提示词、输出目标和启用状态。
- `AiJobRun` 保存每次 AI 自动化执行的输入快照、输出草稿、模型用量、错误和人工处理状态。
- Platform Scheduler 负责 Cron、触发器、执行锁、手动执行、取消执行和执行记录。
- 新增一个 `ai-automation-job` 类型的调度处理器时，只负责从 Platform Scheduler 进入 AI 自动化执行流程。
- AI 自动化输出默认写入草稿、AI 控制台或通知中心，不直接发送外部系统；第六期可通过 Integration 通知规则投递。

适合场景：

- 每周生成项目状态摘要
- 每周识别延期任务
- 每周识别 SPI/CPI 异常
- 每日识别高风险到期项
- 每日汇总逾期回款
- 每月生成经营管理摘要

适合场景都可以手动触发，也可以绑定 Platform Scheduler 触发。

## 11. 安全与治理

必须落实：

- Provider 密钥加密保存
- Token 和成本上限
- 租户隔离
- 用户权限继承
- 项目权限继承
- 经营金额权限裁剪
- Prompt Injection 防护
- 工具调用白名单
- 写回人工确认
- 输出引用来源
- 会话与工具调用审计
- 敏感信息脱敏
- 失败降级
- AI 自动化任务不得绕过 Platform Scheduler 的执行记录和权限控制

## 13. 验收标准

- AI 模块有独立菜单、权限、API 和数据库表。
- 至少支持 2 类标准 Provider 协议：OpenAI Responses 与 Anthropic Messages。
- AI 会话支持澄清模式和规划模式。
- AI 输出能引用项目/经营上下文来源。
- 项目周报、会议纪要、风险分析、经营解释至少各有一个可用技能。
- 工具调用有权限校验和调用记录。
- AI 写回业务对象前必须人工确认。
- 用量和成本可按用户、项目、模型统计。
- Provider 密钥不明文落库。
- 私有化部署时可禁用公网 Provider。

- 新增 `AiWritebackService`，提供创建申请、分页查询、人工确认、驳回和取消能力；状态流转为 `Pending -> Approved / Rejected / Cancelled / Failed`。
- 新增写回确认 API：`GET /api/app/ai/writebacks`、`POST /api/app/ai/writebacks`、`POST /api/app/ai/writebacks/{id}/approve`、`reject`、`cancel`。
- 新增 `写回确认` 菜单，查看权限为 `Ai.Writeback.View`，审批权限为 `Ai.Writeback.Approve`。
- 前端新增 `写回确认` 页面，支持状态、模块、时间范围、关键词筛选，支持分页、详情抽屉、差异预览、载荷预览、确认、驳回和取消。
- 当前确认动作只确认 AI 写回申请本身，不自动执行项目、经营或平台业务写侧变更；后续每个业务写回动作必须在对应模块里补独立执行器和权限校验。
- 场景模板已提供自检预览能力，可在没有真实模型 Provider 的情况下验证项目周报、会议纪要、风险分析、经营解释等模板的渲染结果、推荐工具、Schema 合法性和澄清/规划结构化骨架。
- 场景模板库已提供全量自检能力，可一次性检查 8 个内置管理模板的存在性、渲染结果、推荐工具解析和基础错误。
- 场景模板库已提供真实场景验收入口：`POST /api/app/ai/prompt-templates/acceptance-run` 会创建真实 AI 会话并调用模型，按澄清模式、规划模式、项目周报、会议纪要、风险分析、经营解释六个验收项返回通过/失败、会话 ID、输出预览、错误原因和结构化校验信息。
- 真实场景验收已增加质量门槛：澄清模式必须返回澄清问题或澄清完成摘要，规划模式必须返回可勾选步骤，项目周报、会议纪要、风险分析、经营解释按执行辅助模式验收，并检查场景关键词、输出长度和模型消息状态。
- 前端 `场景模板` 页面新增 `真实验收` 抽屉，可选择模型、上下文类型、真实项目/经营上下文编号、上下文快照、验收输入和验收项；失败项会展示校验原因，并可跳转查看对应会话证据。
- SQLite 迁移已通过临时空库执行验证：使用 DbMigrator 对 `/tmp/general-admin-ai-p5-migration-check.db` 完整执行建表和种子，覆盖 AI 与 Integration 新增迁移。
- PostgreSQL 迁移已通过临时空库执行验证：使用 DbMigrator 对远端临时库 `general_admin_migration_check` 完整执行建表和种子，验证后已删除临时库。
- 迁移验证过程中修复 DbMigrator / HttpApi Host 配置覆盖顺序，确保环境变量和命令行参数优先级高于 `appsettings/*.jsonc`，避免部署时无法覆盖数据库 Provider 和连接字符串。
- 迁移验证过程中修复 SQLite 只读探测连接执行写型 PRAGMA 的问题，避免 EF `Database.Exists()` 阶段因 `journal_mode=WAL` 报 `attempt to write a readonly database`。
- 迁移验证过程中修复 SQLite 初始迁移快照中 `ProjectWbsNode.ParentId` / `Type` 元数据缺失，以及 PostgreSQL 手写迁移缺少 `DbContext` / `Migration` 特性导致后续迁移不被 EF 识别的问题。
- 场景模板自检不等同于真实模型验收。P5-10 中澄清模式、规划模式和各管理模板的真实完整走通，仍需要在目标部署环境配置真实 Provider 后逐项验证。
- AI 会话已接入 OpenAI Responses 工具调用映射和内部受控工具调用闭环：模型可提出白名单工具调用意图，后端统一做权限校验、项目上下文注入、工具执行、审计记录、结果二次提交和会话元数据留痕。
- 流式接口在检测到模型支持 `toolCalling` 且会话具备项目/经营上下文时，会自动复用受控工具调用链路并以 `completed` 事件一次性返回最终结果，避免前端默认流式发送绕过工具审计。
- AI 会话页面已展示消息级工具调用证据，包含工具编码、执行状态、耗时和错误信息，方便 PM/PMO 审查 AI 输出的数据来源和工具执行结果。
- AI 自动化任务已接入 Platform Scheduler，但首版自动化执行仍以结构化草稿为主；如果后续自动化任务调用真实模型，应继续通过 `AiUsageService` 记录 Token、成本和审计。
- P5-9 首版限额配置复用 Provider `ConfigJson`，后续若要支持审批流、部门预算、月度预算、项目预算池和多币种结算，再独立建设 AI 成本策略中心。

## 15. OpenCowork 对标后的补强规划

### 15.1 P5-11 会话运行时体验补强

当前 `AI 会话` 已具备会话、消息、模型、工具、记忆和写回能力，但和 OpenCowork 的 Chat Runtime 对比，之前仍存在两个明显缺口：

- 前端在流式发送完成后重新拉取会话列表和详情，导致用户感知为整页刷新。
- 后端流式入口虽然返回 NDJSON，但在无工具调用路径下仍走非流式模型调用，无法持续输出 `delta`。

本轮补强后：

- 菜单中将原 `AI 会话` 调整为 `AI 对话`，用于轻量对话工作区。
- 新增 `会话管理` 菜单，承接会话搜索、打开、归档、恢复、导出和删除。
- `AI 对话` 页面发送消息完成后只增量更新当前会话消息和左侧会话摘要，不再整页重拉。
- OpenAI Responses 协议流式请求改为调用 `/responses`，不再错误走 `/chat/completions`。
- Anthropic Messages 协议流式请求改为调用 `/messages`，支持解析 `content_block_delta` 和 `message_delta`。
- 工具调用路径仍复用现有非流式受控 tool-calling 链路，避免流式发送绕过工具审计。

### 15.2 P5-12 消息渲染补强

OpenCowork 的消息区支持 Markdown、代码块、工具块、Widget、Thinking、上下文压缩提示等结构化渲染。General Admin 当前不适合直接渲染任意 HTML/Widget，因此先按企业后台安全边界补齐 Markdown 渲染。

本轮补强后：

- 新增 `AiMarkdownMessage` 前端组件。
- AI 消息支持 Markdown、GFM 表格、列表、引用和代码块基础渲染。
- 渲染前会移除脚本、表单、iframe、事件属性和 `javascript:` 链接，避免模型输出变成任意前端执行入口。
- 当前实现优先使用项目已有 `marked` 依赖，不引入 `markstream-vue` 的 beta 依赖链；后续如要更强的增量 Markdown，可单独替换渲染组件。

### 15.3 P5-13 到 P5-16 基础版已落地

OpenCowork 对标后的关键缺口已完成基础版建设：

- `AiSkill`：系统内可选择的管理工作流说明，区别于七期外部 `SKILL.md` 包；已内置项目周报、风险分析、会议纪要、经营解释和联网资料简报。
- `AiPersona`：企业系统内的 AI 角色画像，用于替代 OpenCowork 的 SOUL 命名；已内置 PM、PMO、经营分析三类画像。
- `AiCommand`：对话输入区的 `/周报`、`/风险分析`、`/会议纪要` 等快捷命令；已具备配置实体、API 和管理页面。
- `AiAgentDefinition`：PM、PMO、经营分析等受控 Agent 定义；已具备角色画像、技能、工具、模型和运行时配置组合能力。
- `AiArtifact`：白名单 JSON 图表/卡片协议，用于替代任意 HTML Widget；已内置指标卡、行动队列和风险矩阵。
- `WebSearch`：带 Provider 配置、密钥加密、Endpoint 域名策略和审计记录的联网搜索能力；已支持 Tavily、Bing Web Search、SerpApi 和自定义 JSON Provider。
- `IAiAgentRuntime`：已新增后端运行时抽象，当前基础版先生成受控运行计划，后续承接多轮模型、工具循环、审批、上下文压缩和取消执行。

新增菜单：

- `Agent 编排`：维护 Agent、技能、角色画像和快捷命令。
- `安全构件`：维护模型可输出的白名单 JSON 构件。
- `联网搜索`：维护搜索 Provider、测试搜索和查看调用审计。

仍需继续增强：

- Artifact 输出增加 JSON Schema 严格校验和失败提示。
- `web.search` 搜索结果 URL 做结果级 allow/deny 过滤，并把真实结果来源注入引用。
- 在 `IAiAgentRuntime` 后补多轮模型调用、工具循环、人工审批、上下文压缩和取消执行。

技术取舍：

- 不照搬 OpenCowork 的 Shell、文件系统、桌面控制和任意 HTML Widget。
- 不把 Microsoft Agent Framework / MEAI 直接作为生产依赖；先在 `IAiAgentRuntime` 和 `IAiModelGateway` 后面预留替换点，后续做独立 spike。
- 不新增第二套 Cron。AI 自动化任务继续复用 Platform Scheduler。
