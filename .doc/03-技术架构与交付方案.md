# 03 技术架构与交付方案

## 1. 修订说明

本文按当前已经落地的工程实践，以及五期 AI 模块、六期外部集成模块、七期项目 CLI Skill 化规划修订。

当前仍采用 ABP 模块化单体架构，但模块边界需要从 `Platform / Project / Business` 扩展为：

- Platform
- Project
- Business
- AI
- Integration

七期 `项目 CLI Skill 化` 不新增后端业务模块，只在文档、脚本规范和 Skill 包层面沉淀 AI 可调用说明。

## 2. 总体架构

当前采用模块化单体架构，这一判断仍然成立。

原因：

- 项目仍处于业务边界逐步稳定阶段
- 私有化项目优先追求稳定和易维护
- AI 和外部集成需要复用现有权限、租户、文件、审计和业务数据
- 七期 Skill 需要稳定依赖已有 API、CLI 命令约定和权限边界
- 当前难点在业务结构、权限边界、数据口径和交互闭环，不在物理拆分

## 4. 当前工程组织原则

### 4.1 后端

- 权限、菜单、平台治理能力优先沉淀在平台中心相关服务中
- 业务能力按分区逐步生长，不急于拆成多服务
- AI 和 Integration 必须作为独立模块新增，不继续塞进 Platform
- Project/Business 对 AI 和 Integration 保持低耦合，通过应用服务、领域事件、上下文读取器和工具适配器协作
- 七期只输出 Skill 包和命令说明，不让 Project/Business 反向依赖 Skill

### 4.2 前端

- 先在统一前端壳中承接平台、项目、经营、AI、集成五大分区
- 页面以业务控制台为目标，不做过多散装列表
- AI 页面重点服务 PM、PMO、经营管理人员的管理动作
- 集成页面重点服务管理员配置、投递治理、同步监控和失败处理

### 4.3 OpenCowork 架构参考映射

OpenCowork 的架构不能直接照搬到 General Admin。General Admin 是 ABP 服务端系统，不是 Electron 本地 Agent，但可以吸收它的分层思想。

| OpenCowork 架构点 | 在 General Admin 中的映射 |
|---|---|
| Renderer Agent Loop | 五期 AI 会话编排、澄清模式、规划模式 |
| Tool Registry | 五期 `AiToolRegistry` 和受控工具白名单 |
| Provider System | 五期 `AiProvider`、`AiModel` 和模型网关 |
| McpManager | 五期 `AiMcpService`，管理 MCP Client 和工具发现 |
| CronScheduler | 不新增调度器；只借鉴“定时触发 Agent 任务”的产品形态，实际复用 Platform Scheduler |
| ChannelManager | 六期 `IntegrationConnectorRegistry`，承接飞书、钉钉、企业微信等连接器 |
| Skills | 七期 General Admin Skill 包，沉淀 AI 可读操作说明 |
| Shared protocols/types | 后端 Contracts DTO、前端 API 类型、Skill 输入输出约定 |

### 5.3 服务端优先原则

OpenCowork 的 Electron 本地 Agent 能力只作为产品灵感。General Admin 的 AI 能力应优先在云上或私有化服务器运行：

- Provider 配置在服务端保存
- MCP 配置由租户或管理员维护
- 工具调用走服务端权限校验
- 成本、用量、审计在服务端统一记录
- AI 写回业务对象必须可追踪、可撤销、可审批
- AI 自动化任务只保存任务定义和执行结果，调度触发复用 Platform Scheduler

### 6.4 与五期 AI 和七期 Skill 的边界

- Integration 负责外部系统连接、账号绑定、消息投递、Webhook 回流和同步任务。
- AI 可以调用 Integration 提供的受控投递草稿或通知建议，但不能绕过 Integration 直接保存外部密钥。
- 七期 Skill 可以说明如何通过 CLI/API 查询投递日志或触发测试发送，但不保存连接器密钥，也不直接实现消息平台协议。

## 8. 开发规范与代码质量标准

本节作为后续前后端开发、代码审查和 AI 辅助改造的统一标准。新增功能和历史页面治理都应优先按本节执行，确有例外时需要在代码或评审说明中解释原因。

### 8.1 前端架构与目录

- 主业务前端只在 `General.Web/apps/web-general` 内演进，不直接修改 `General.Web/packages` 下的 Vben 模板和框架源码，避免后续模板同步冲突。
- API 封装统一放在 `src/api/core/*.ts`，类型使用 `namespace XxxApi {}`，字段名保持与后端 DTO 一致。
- 页面按业务分区放置：
  - 平台治理：`src/views/platform`
  - 项目执行：`src/views/project`
  - 经营管理：`src/views/business`
  - AI 能力：`src/views/ai`
  - 外部集成：`src/views/integration`
- 复杂页面必须拆分 composable 和局部组件，不能继续把请求、状态、表单、表格、抽屉和权限逻辑全部堆在一个 Vue 文件里。

### 8.2 前端样式标准

- 前端以 Vben Admin 模板范式为优先标准：能使用 `@vben/common-ui`、`useVbenVxeGrid`、`useVbenForm`、`useVbenDrawer`、全局 adapter 的，不自行重建一套页面壳、表格、表单、抽屉或分页体系。
- 页面样式采用 Tailwind-first 原则，优先在模板中使用 Tailwind 类，少量复杂组件样式可在 `style scoped` 中通过 `@apply` 表达。
- 禁止在业务页面中散落硬编码 `margin/padding/gap/border-radius`。确需覆盖第三方组件时，优先使用组件属性、Vben 插槽、外层 Tailwind 类或统一样式入口。
- `Card` 只用于仪表盘指标、详情信息块、复杂工作台分区和非表格型内容承载；标准列表页不再默认用 `Card > Grid` 包裹。
- 指标大数字统一按 `24px` 体系处理；普通说明、标签、辅助信息按局部密度使用 `12px/13px/14px`，不要在同一层级混用多个大字号。
- 表格空态统一使用组件默认空态，普通数据表文案默认 `暂无数据`。只有业务语义强的非表格空态才使用“暂无项目数据”“暂无会话”等场景文案。

### 8.3 VXE 表格标准

- 标准列表页结构优先使用 Vben 模板写法：`<Page auto-content-height>` 直接承载 `<Grid table-title="...">`，操作按钮放入 `#toolbar-tools`，查询条件放入 `formOptions`。
- 业务表格统一使用 `useVbenVxeGrid` 和 `src/adapter/vxe-table.ts` 中的全局配置。除极少数只读小型静态表格外，不使用 Ant Design Vue `Table` 承接业务数据列表。
- 远程分页、排序、筛选优先使用 `gridOptions.proxyConfig.ajax.query` 和 `formOptions`，由 Grid 管理加载、分页和刷新。`useLocalVxePagination` 只作为历史兼容或纯前端派生数据的临时方案，不作为新页面标准。
- 操作按钮优先通过列配置、插槽和 `#toolbar-tools` 表达；新增、刷新、批量操作等页面级动作放在 Grid 工具栏，不再优先放到 `Card #extra`。
- 现存 `Card > Grid` 页面在未重构前必须挂 `class="app-vxe-card-grid"`，统一走 `src/styles/app-vxe.css` 控制左右边距、分页器间距和空态高度；这是过渡兼容层，不是新页面标准。
- 表格与卡片边缘的横向距离只调整 `app-vxe.css` 中的 `--app-vxe-grid-edge-gap`，不要在单个页面通过负边距、Card body 覆盖或局部 padding 修正。
- 操作列按钮较多时，优先加宽固定操作列并保持单行展示；不应让“操作”列在常规桌面宽度下挤成两行。复杂操作可以拆到 Drawer 或下拉菜单。
- 表格分页、排序、筛选和空态必须通过 Vben Grid 统一配置表达，不要在表格外额外写一套分页和空态，除非该页面是非表格型工作台。

### 8.4 Drawer 与 Modal 使用规则

- 新增、编辑、多字段表单、详情查看、授权配置、批量导入和需要保留页面上下文的流程优先使用 Vben `useVbenDrawer`；历史页面已经使用 Ant Design Vue `Drawer` 的，逐步迁移，不再继续扩散。
- `Modal` 仅用于确认、预览、安全敏感短动作、单字段小表单和短暂任务，例如文件预览、重置密码、轮换密钥、标记跳过。
- Drawer 底部操作统一使用右对齐按钮区：取消在左、主要动作在右，按钮间距使用 Tailwind `gap-2` 或 `Space`。
- 不要为了减少改动把复杂表单塞进 Modal；当表单需要滚动、对照表格上下文或后续扩展字段时，一开始就用 Drawer。

### 8.5 后端架构与代码标准

- 后端继续遵循 ABP DDD 分层：
  - `Domain.Shared` 放枚举、常量、权限、本地化和共享定义
  - `Domain` 放实体、聚合和领域规则
  - `Application.Contracts` 放 DTO 和应用服务接口
  - `Application` 放应用服务、查询聚合和写侧编排
  - `EntityFrameworkCore` 放 EF 映射、迁移和数据库适配
- 实体优先继承 `FullAuditedAggregateRoot<Guid>`，保持受控修改方法，避免把实体退化成任意 set 的数据袋。
- 权限统一走权限定义和 AccessGuard，不在控制器、前端或零散方法里复制权限判断。
- 查询聚合优先使用 Context/Loader 模式一次性加载关联数据，避免 N+1。
- 指标口径由后端定义。健康分、SPI/CPI、利润、回款、逾期、预警等级等不能在多个前端页面重复拼装。
- 数据模型变更必须同步实体、EF 映射、DTO、应用服务、迁移、前端 API 类型和页面展示。

### 8.6 命名与验证

- C# 公共成员使用 PascalCase，私有字段和局部变量使用 camelCase；异步方法保持 `Async` 后缀。
- Vue/TypeScript 使用 2 空格缩进、单引号、严格类型，避免 `any` 扩散。
- 用户可见文案、状态标签、字典值和代码注释优先使用中文；英文只用于技术标识符和第三方 API。
- 前端页面变更至少运行 `pnpm typecheck` 或 `pnpm build`；后端逻辑或契约变更至少运行 `dotnet build General.Admin.slnx`。
- 构建产生的 `dist`、压缩包、日志和本地数据库文件不进入代码提交。

## 9. 交付原则

### 9.1 Web 是当前正式主交付端

所有核心业务能力优先在 Web 中完整落地。

### 9.2 桌面端不是主产品线

桌面端只承担：

- 壳层承载
- 通知
- 文件选择增强
- 本地能力桥接

### 9.3 私有化优先

部署设计优先考虑：

- 单机可用
- 内网可用
- 易迁移
- 易备份
- 可审计
- 可限制外网访问

### 9.4 AI、集成与 Skill 的安全优先级

- 密钥必须加密保存
- 外部回调必须校验签名
- AI 工具调用必须有权限边界
- AI 输出不能默认写回业务对象
- 敏感金额、利润、人员信息必须按权限裁剪
- 外部消息发送必须记录投递日志
- Skill 只能说明受控操作，不写入密钥、不绕过权限、不承诺自动审批

## 10. 当前技术结论

当前这套技术路线成立的关键原因不是“技术先进”，而是它能稳定支撑：

- 平台治理
- 项目执行
- 经营管理
- PMP 项目管理闭环
- AI 智能能力
- 外部系统集成
- 项目 CLI Skill 化

五期和六期新增的是模块，不是把系统改成微服务，也不是把产品方向改成通用 AI 平台或通用集成平台。七期新增的是 Skill 化交付资产，不改变后端模块边界。
