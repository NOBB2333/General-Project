# 02 业务模块与管理规则

## 1. 修订说明

本文保留原编号，但按当前项目成熟后的理解重写，不再混合早期散装模块设想。

五期和六期开始后，系统从三条稳定主线扩展为“五条主线”，其中 AI 和外部集成必须作为独立业务模块建设。

七期 `项目 CLI Skill 化` 不新增业务主线，只沉淀 AI 可读操作说明和 Skill 包，服务 OpenCowork、Codex 或内部 AI 调用。

## 2. 业务模型

系统按五条主线组织：

### 2.1 平台治理主线

解决：

- 用户
- 组织
- 角色
- 菜单
- 日志
- 监控
- 文件
- 定时任务
- 租户与基础配置

### 2.2 项目执行主线

解决：

- 项目建档
- 项目详情
- 章程、目标、范围、WBS、排期、任务、问题、文档、成员、工时
- RAID、质量、变更、基线、EVM、会议、报告、资源
- PM 与 PMO 的执行视图

### 2.3 经营管理主线

解决：

- 经营总览
- 单项目经营下钻
- 合同、预算、采购、开票、回款、验收
- 经营报表和预警
- 经营数据与项目执行数据的联动

### 2.4 AI 智能主线

解决：

- Provider 与模型配置
- AI 会话、助手、场景模板、提示词
- 澄清模式、规划模式、执行辅助模式、知识问答模式
- 项目报告、周报、会议纪要、风险分析、经营分析
- MCP 工具接入、系统能力暴露、受控工具调用
- 记忆、知识源、用量、成本、审计和安全

AI 模块不直接拥有项目、经营和平台实体，只通过明确的上下文读取器、工具适配器和权限校验访问其他模块。

### 2.5 外部集成主线

解决：

- 飞书、钉钉、企业微信等连接器
- 外部租户、外部应用、外部账号绑定
- 组织、用户、部门、群组同步
- 个人消息、群消息、机器人卡片、日程和会议回流
- 风险、会议纪要、行动项、任务提醒、报告分发
- Webhook 回调、消息投递、重试、死信、幂等和审计

外部集成模块不直接替代平台通知，也不直接替代项目业务写侧。它负责连接、映射、同步和消息投递。

## 5. 管理规则

### 5.1 菜单规则

- 菜单应按分区组织，不按散装对象平铺
- 一级菜单必须控制数量
- 平台菜单不承接业务驾驶舱页面
- AI 能力统一放在 AI 智能能力区
- 飞书、钉钉、企业微信等能力统一放在外部系统集成区
- Skill 化能力统一放在七期文档和 Skill 包，不放入平台中心菜单

### 5.2 页面规则

- 项目执行区以 `项目详情` 为核心
- 经营管理区以 `经营总览 / 项目经营 / 报表中心` 为核心
- AI 区以 `AI 会话 / AI 控制台 / 配置治理` 为核心
- 集成区以 `连接器 / 账号绑定 / 通知规则 / 同步任务 / 投递日志` 为核心
- 七期 Skill 以 `SKILL.md / 示例命令 / 验收清单` 为核心，不新增业务页面
- 报表中心负责跨项目检索，不负责替代项目详情和项目经营页

### 5.3 数据规则

- 指标口径统一由后端定义
- 预警类对象优先结构化，不在多个页面各自拼装
- 敏感金额和利润信息必须按权限控制
- AI 不绕过用户权限读取数据
- AI 写回业务数据必须走审批或人工确认
- 外部系统回调必须做签名、幂等、租户隔离和审计
- 外部 ID 映射必须结构化保存，不能靠名称匹配长期运行
- Skill 调用必须继承现有权限、审计和人工确认边界，不允许在说明中暗示绕过审批

### 5.4 模块依赖规则

- Project 和 Business 不依赖 AI 模块
- Project 和 Business 不依赖 Integration 模块
- AI 可以通过接口读取 Project/Business 上下文，但不能直接绕过应用服务改库
- Integration 可以订阅业务事件并调用受控写侧接口，但不能把外部数据直接写进业务表
- Platform 提供文件、通知、审计、定时任务等基础设施，但不承接 AI 和 Integration 的领域模型
- Skill 包不反向依赖业务模块，不要求业务模块为 Skill 做特殊分支；需要稳定能力时优先复用已有 API 或后续升级 MCP

## 6. 当前结论

系统业务模块不是越多越好，而是必须围绕：

- 平台治理
- 项目执行
- 经营管理
- AI 智能能力
- 外部系统集成

五条主线稳定展开。五期和六期新增模块后，模块边界比功能数量更重要。

七期只做能力封装和操作规范沉淀，不改变五条主线。
