## 1. 核对结论

### 1.1 项目执行板块现状

| 维度 | 当前事实 | 结论 |

| 后端服务 | `ProjectService.cs` 861 行 | 已形成单体应用服务，查询、聚合、权限、创建逻辑耦合在一个类中 |
| 前端页面 | `project/detail/index.vue` 2120 行 | 页面承载详情、任务、看板、日历、甘特、RACI 等过多职责 |

### 1.3 对上一版分析的修正

| 原判断 | 修正 |
|---|---|
| “ProjectTask 已有完整描述、标签、Story Points 等字段” | 当前代码中的 `ProjectTask` 没有这些字段；这是 PRD 设想，不是当前实现 |

## 3. 下一步总原则

1. 先补数据模型，再补页面体验。PMP 能力依赖结构化数据，不能只在前端展示概念。
2. 先做“治理闭环”，再做 AI 和高级分析。没有 WBS、变更、质量、EVM 基础数据，AI 报告只能做文本拼接。
3. P0 目标从“CRUD 补齐”升级为“项目管理闭环最小可用”。
4. 经营管理不要只做财务数字展示，要和项目执行的变更、进度、验收、收尾联动。
5. 代码重构不单独追求拆文件，应服务于业务边界：执行、计划、风险、质量、经营链各自独立演进。

### P0-F EVM 最小模型

**目标：** 建立成本/进度监控的基础指标，不把 EVM 简化为几个静态字段。

**建议新增：**

| 实体/服务 | 用途 |
|---|---|
| `ProjectBaseline` | 保存范围/进度/成本基线版本 |
| `ProjectPerformanceSnapshot` | 按周/月记录 PV、EV、AC、SPI、CPI |
| `ProjectPerformanceService` | 根据任务进度、预算执行、工时/成本归集计算绩效 |

**计算口径建议：**

| 指标 | 说明 |
|---|---|
| PV | 截止统计日，按基线计划应完成的预算价值 |
| EV | 截止统计日，按实际完成比例挣得的预算价值 |
| AC | 截止统计日，实际发生成本，初期可用工时成本 + 采购/预算执行近似 |
| SPI | EV / PV |
| CPI | EV / AC |

**验收标准：**

- [ ] 项目详情能展示 SPI、CPI、PV、EV、AC。
- [ ] 每周生成一条绩效快照。
- [ ] 经营总览能按 SPI/CPI 识别进度和成本异常项目。

## 10. 暂不建议做的事

| 项 | 原因 |
|---|---|
| 直接先做 AI 报告 | 没有 EVM、质量、变更、干系人、沟通计划数据，报告只能拼接现有字段 |
| 直接大拆服务 | 当前业务边界还未补齐，过早拆分容易把缺失模型固化 |
| 只在前端增加 PMP 页面 | PMP 概念必须落到实体、接口、审批和指标，否则只是展示层包装 |
| 只加 PV/EV/AC 三个字段 | EVM 需要基线、快照、计算口径和历史趋势 |
| 继续用名称字符串表示责任人 | 会阻断权限、通知、资源负荷和人员变更追溯 |

## 11. 一句话结论

当前系统已经有项目执行和项目经营的基础骨架，但还偏向“项目协作 + 经营看板”。下一步四期建设应从单纯补 CRUD，升级为补齐 PMP 的治理闭环：章程定边界，WBS 定范围，依赖和基线定计划，EVM 定绩效，RAID 定风险，质量标准定验收，变更控制定秩序，干系人和沟通计划定协同。
